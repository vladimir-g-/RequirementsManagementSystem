# Requirements Management System

Веб-приложение для управления требованиями по проектам.

**ВНИМАНИЕ** - пока это MVP!

Возможности:

- вход аутентифицированного пользователя;
- выбор проекта и просмотр его требований;
- изменение ширины столбцов таблицы требований с сохранением настройки для пользователя;
- создание, редактирование и удаление требований;
- создание, редактирование и удаление иерархических групп требований; создание дочерней группы доступно кнопкой «+» рядом с редактированием группы;
- привязка требования к одной группе или отвязка от группы;
- фильтрация по статусу и поиск по номеру, описанию и типу;
- роли `Администратор` и `Пользователь`;
- управление списком проектов: создание, изменение названия, изменение кода пустого проекта и удаление проекта без требований и групп; при удалении проекта также удаляются доступ пользователей к нему, их права и настройки префиксов;
- управление справочником типов требований: создание, переименование и удаление неиспользуемых типов; при удалении типа удаляются настройки префиксов для этого типа;
- назначение пользователям проектов и отдельных прав на требования в каждом проекте; пользователя можно создать без доступа к проектам и назначить проекты и права позднее;
- интерфейс управления пользователями доступен администраторам;
- создание, просмотр и удаление связей между требованиями; администратор управляет общим каталогом типов связей;
- хранение изменяемых данных в PostgreSQL.

Справочные данные хранятся в таблицах PostgreSQL, а не в JSON-файлах:

- `projects` — проекты; администратор управляет ими в меню **Администрирование → Проекты**;
- `requirement_types` — типы требований; управление в меню **Администрирование → Типы требований**;
- `requirement_link_types` — типы связей; управление в меню **Администрирование → Типы связей**;
- `requirement_prefixes` — префиксы номеров требований для пары «проект + тип»;
- `requirement_statuses` — статусы требований;
- `requirement_priorities` — важности требований;
- `requirement_complexities` — сложности требований.

Начальные значения справочников задаются SQL-миграциями, включая `003_requirement_reference_data.sql`. Статусы, важности и сложности читаются из PostgreSQL; их JSON-файлы в `public/config` сохранены, но больше не используются приложением как источник данных. JSON-файлы проектов и типов требований также сохранены для совместимости, а `data/database.json` — для однократного импорта существующих данных. Требования и префиксы ссылаются на тип по постоянному `id`, поэтому переименование типа не меняет нумерацию требований.

Справочники статусов, важностей и сложностей сервер отдает через `GET /api/config`. Остальные справочники доступны через `GET /api/projects`, `GET /api/requirement-types` и `GET /api/requirement-link-types`.

Права пользователя: `create`, `read`, `update`, `delete`. Права назначаются отдельно для каждого проекта: пользователь видит и изменяет требования только в проектах, где у него есть соответствующее право. Пользователя можно создать без доступа к проектам; проекты и права назначаются позднее при редактировании.

Связи создаются между разными требованиями одного проекта. Создание и удаление связей требуют прав `read` и `update`; просмотр существующих связей доступен при праве `read`. Между одной парой требований допускается только одна связь. Типы связей и их направленность настраиваются администратором в меню **Администрирование → Типы связей**; удаление типа удаляет все связи этого типа, но не требования.

Группы принадлежат проекту и могут иметь подгруппы любой глубины. При выборе группы в дереве отображаются требования этой группы и всех её дочерних групп. Удаление требует подтверждения пользователя; удалить можно только группу без требований и дочерних групп. Права на группы используют права проекта: `create`, `update` и `delete`.

Номера требований формируются сервером автоматически в формате `ПРЕФИКС-001`. Префикс задаётся администратором отдельно для каждой пары `проект + тип требования`, а числовая часть увеличивается в рамках этой пары. Настройка доступна в меню администратора: **Префиксы требований**.

Рекомендации по дальнейшему развитию: [docs/future-recommendations.md](docs/future-recommendations.md).

## Run

Требуется PostgreSQL. Сервер PostgreSQL должен быть запущен локально или доступен по сети. Используйте базу данных `postgres` и создайте отдельную учетную запись приложения `rms_user` средствами PostgreSQL; приложение не устанавливает сервер, не создает базу данных и не создает учетную запись. Укажите строку подключения в `DATABASE_URL`. Для локальной разработки в PowerShell:

```powershell
$env:DATABASE_URL = 'postgresql://rms_user:<password>@localhost:5432/postgres'
npm.cmd install
npm.cmd run db:migrate
```

Для нового пустого проекта после миграций переходите к `npm start`. Для переноса существующих данных выполните импорт до первого запуска приложения:

```powershell
npm.cmd run db:import
npm.cmd start
```

Импорт по умолчанию читает `data/database.json`; другой файл можно передать как аргумент: `npm run db:import -- path\to\database.json`. Импорт выполняется транзакционно, сохраняет идентификаторы и связи, отказывается смешивать снимки из разных источников и при повторном запуске того же файла не меняет данные. Исходный JSON-файл не удаляется. Сохраните его как резервную копию до проверки результата в приложении.

`DATABASE_URL` имеет вид `postgresql://пользователь:пароль@сервер:5432/имя_базы`. Команда PowerShell выше задает переменную только для текущего окна; запустите в нем же команды npm. Если пароль содержит специальные символы URI, закодируйте их. Не добавляйте реальные пароли в файлы репозитория. При развертывании передавайте строку подключения через защищенную конфигурацию окружения.

### Схема PostgreSQL

Имя базы данных в `DATABASE_URL` — это часть после порта; схема настраивается отдельно через `search_path`. В этой конфигурации база данных называется `postgres`, а схема — `rms`. Все SQL-запросы приложения и миграций используют имена таблиц без префикса, поэтому подключитесь к базе `postgres` как администратор PostgreSQL и создайте схему, назначив ее первой в `search_path` для роли приложения:

```sql
CREATE SCHEMA IF NOT EXISTS rms AUTHORIZATION rms_user;
ALTER ROLE rms_user IN DATABASE postgres SET search_path TO rms, public;
```

Замените `rms_user`, если в `DATABASE_URL` указана другая роль. Настройка роли применяется к новым подключениям: переподключитесь, затем запустите `npm.cmd run db:migrate`, импорт (если он нужен) и приложение. Таблицы, включая `schema_migrations`, будут созданы в схеме `rms`.

Для отдельной схемы только у этого процесса можно вместо настройки роли добавить search path в URI: `?options=-c%20search_path%3Drms%2Cpublic`. Схема `rms` все равно должна существовать, а роль подключения должна иметь право создавать в ней таблицы.

Если PostgreSQL возвращает код `53300` («слишком много подключений для роли»), остановите работающие экземпляры приложения перед `db:migrate` и закройте лишние соединения pgAdmin/psql. Проверить лимит и активные подключения можно от имени администратора БД:

```sql
SELECT rolname, rolconnlimit FROM pg_roles WHERE rolname = 'rms_user';
SELECT pid, application_name, state FROM pg_stat_activity WHERE usename = 'rms_user';
```

Значение `rolconnlimit = 0` запрещает роли открывать соединения; `-1` означает отсутствие отдельного лимита роли. У `node-postgres` пул приложения по умолчанию может открыть до 10 соединений на процесс. Если лимит роли ниже потребности приложения, администратор может увеличить его, например: `ALTER ROLE rms_user CONNECTION LIMIT 10;`. Подставьте имя роли из `DATABASE_URL` и выберите лимит с учетом лимита подключений всего сервера PostgreSQL.

После миграции схемы можно запускать приложение:

```powershell
npm.cmd start
```

The server starts at `http://localhost:3000`.

Тестовый пользователь: `admin` / `admin123`.

For development with automatic restarts:

```powershell
npm.cmd run dev
```

Тесты на PostgreSQL используют только отдельную тестовую базу, заданную через `TEST_DATABASE_URL`; тест создаёт и удаляет в ней временную схему, поэтому учетной записи нужны права на создание схем. Например:

```powershell
$env:TEST_DATABASE_URL = 'postgresql://rms_test:<password>@localhost:5432/requirements_management_test'
npm.cmd test
```

Не указывайте production-базу для тестирования.
