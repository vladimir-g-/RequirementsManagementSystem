# Функциональная спецификация реализованного MVP

## 1. Назначение системы

Requirements Management System (RMS) — веб-приложение для управления требованиями проектов в рамках единой рабочей области. Система позволяет:

- хранить требования по проектам;
- организовывать их в многоуровневую иерархию групп;
- контролировать привязку пользователей к проектам и правам доступа;
- фильтровать, искать и сортировать требования;
- управлять форматами идентификаторов требований и базовыми справочниками.

Система реализована как локальный MVP с хранением данных в JSON-файле `data/database.json` и сервером Node.js, обслуживающим статические ресурсы и REST API.

## 2. Область действия

В текущей реализации поддерживаются следующие функции:

- аутентификация и сеансы пользователей;
- выбор активного проекта и ограничение видимости данных по проектам;
- просмотр, создание, редактирование и удаление требований;
- создание, редактирование и удаление групп требований с поддержкой вложенности любой глубины;
- фильтрация и поиск требований по критериям проекта, типа, приоритета, статуса, сложности, релиза и текста;
- сортировка таблицы требований;
- управление пользователями и правами доступа для администратора;
- настройка префиксов номеров требований для комбинации проект + тип;
- хранение пользовательских настроек ширины столбцов таблицы в локальном хранилище браузера.

## 3. Пользователи и роли

### 3.1 Администратор

Пользователь с ролью `Администратор` имеет полный доступ к данным системы и административным функциям:

- просмотр всех проектов;
- просмотр и изменение всех требований;
- управление пользователями;
- назначение прав и привязку к проектам;
- настройка префиксов требований;
- создание и редактирование групп в любом проекте.

### 3.2 Пользователь

Пользователь с ролью `Пользователь` ограничен правами на уровне:

- проектов, назначенных на пользователя;
- прав `create`, `read`, `update`, `delete` на требования;
- прав на группы по проектам, где пользователь имеет доступ.

Если пользователь не имеет права `read`, система запрещает ему просмотр требований и групп в проекте.

## 4. Функциональные требования

### 4.1 Аутентификация

1. Пользователь входит в систему по логину и паролю.
2. После успешного входа сервер создает сеансовый токен и сохраняет его в cookie (`session`).
3. Для всех защищенных запросов сервер получает текущего пользователя из cookie и проверяет его права.
4. Если токен отсутствует или недействителен, система возвращает ошибку 401/403 при обращении к защищенным ресурсам.
5. Пользователь может завершить сеанс через действие «Выйти».

Пользователь по умолчанию и для локального MVP:

- логин: `admin`
- пароль: `admin123`

### 4.2 Выбор проекта и видимость данных

1. Система поддерживает несколько проектов, перечисленных в конфигурации.
2. Пользователь выбирает текущий проект из списка в верхней панели.
3. Администратор видит все доступные проекты.
4. Пользователь видит только назначенные ему проекты.
5. Данные о требованиях и группах фильтруются по активному проекту.

## 5. Управление требованиями

### 5.1 Создание требования

Пользователь может создать требование, если имеет право `create` для выбранного проекта.

Обязательные поля:

- краткое описание;
- тип требования;
- важность;
- статус;
- проект.

Дополнительные поля:

- подробное описание в Markdown;
- сложность;
- номер релиза;
- группа.

### 5.2 Просмотр требования

Требование отображается в таблице с параметрами:

- номер;
- краткое описание;
- группа;
- тип;
- важность;
- сложность;
- статус;
- релиз.

Таблица поддерживает сортировку по столбцам.

### 5.3 Редактирование требования

Пользователь может изменять требование, если имеет право `update` в проекте.

При редактировании допустимо менять:

- описание;
- детальную информацию Markdown;
- тип;
- важность;
- сложность;
- статус;
- релиз;
- привязку к группе.

Номер требования после создания не изменяется.

### 5.4 Удаление требования

Пользователь может удалить требование, если имеет право `delete` в проекте.

Удаление выполняется подтверждением пользователя и удаляет запись из системы без дополнительной проверки.

### 5.5 Автоматическая генерация номера требования

Номер требования формируется автоматически по шаблону:

`ПРЕФИКС-001`

Где:

- `ПРЕФИКС` — уникальный префикс для пары `проект + тип требования`;
- `001` — порядковый номер в рамках этой комбинации.

Пример: `REQ-001`, `BUG-003`.

Примечание: если для проекта и типа не задан префикс, система использует код проекта как запасной префикс, либо `REQ`.

## 6. Управление группами требований

### 6.1 Иерархия групп

Система поддерживает древовидную структуру групп требований.

Правила:

- каждая группа принадлежит одному проекту;
- группы могут иметь родительскую группу;
- уровень вложенности не ограничен;
- при выборе группы отображаются требования этой группы и всех дочерних групп.

### 6.2 Создание группы

Пользователь может создать группу, если имеет право `create` в проекте.

При создании указывается:

- название группы;
- родительская группа (при необходимости);
- проект.

### 6.3 Редактирование группы

Пользователь может редактировать группу, если имеет право `update`.

В ходе редактирования допускается изменение:

- имени группы;
- родительской группы.

Запрещено переносить группу в себя или в ее дочернюю группу, чтобы исключить циклические ссылки.

### 6.4 Удаление группы

Пользователь может удалить группу, если имеет право `delete` в проекте.

Удаление возможно только если:

- в группе нет требований;
- у группы нет дочерних групп.

В противном случае система возвращает ошибку и запрещает удаление.

## 7. Поиск, фильтрация и сортировка

### 7.1 Поиск

Пользователь может искать требования по полям:

- номер;
- описание;
- тип.

Поиск реализуется по текстовому совпадению в нижнем регистре.

### 7.2 Фильтрация

Поддерживаются фильтры по следующим параметрам:

- тип;
- важность;
- сложность;
- статус;
- релиз.

Фильтры могут быть множественными: пользователь может выбрать несколько значений в каждом поле.

### 7.3 Сортировка

В таблице требований поддерживается сортировка по столбцам:

- номер;
- описание;
- тип;
- важность;
- сложность;
- статус;
- релиз.

Сортировка циклическая: по возрастанию, по убыванию, затем сброс.

## 8. Управление пользователями и правами

### 8.1 Создание пользователя

Администратор может создать нового пользователя.

Необходимо указать:

- имя;
- логин;
- роль;
- пароль;
- доступные проекты (для роли `Пользователь`);
- права на требования.

### 8.2 Редактирование пользователя

Администратор может изменить данные пользователя, включая:

- имя;
- логин;
- роль;
- пароль;
- проекты доступа;
- права.

### 8.3 Удаление пользователя

Администратор может удалить пользователя, кроме текущего авторизованного пользователя.

### 8.4 Разрешения

Для `Пользователь` набор прав хранится как объект:

- `create`;
- `read`;
- `update`;
- `delete`.

Права могут быть назначены независимо друг от друга.

## 9. Администрирование префиксов требований

Администратор может настроить префикс для каждой пары:

- проект;
- тип требования.

Настройки сохраняются в `data/database.json` в структуре `requirementPrefixes`.

Правила:

- префикс должен состоять из букв, цифр, символов `_` и `-`;
- длина префикса ограничена 20 символами;
- префикс обязателен для записи;
- значения должны быть уникальными в рамках проекта и типа.

## 10. Конфигурационные справочники

Приложение загружает справочные данные через серверный API `/api/config`.

Поддерживаются следующие наборы значений:

- статусы требований;
- приоритеты;
- уровни сложности;
- типы требований;
- проекты.

Привязка этих справочников вынесена в JSON-файлы директории `public/config`:

- `statuses.json`
- `priorities.json`
- `complexities.json`
- `types.json`
- `projects.json`

## 11. Взаимодействие с интерфейсом

### 11.1 Основная страница

На главной странице пользователь видит:

- верхнюю панель выбора проекта;
- пользовательское меню;
- панель фильтров и поиска;
- дерево групп;
- таблицу требований.

### 11.2 Управление шириной столбцов

Пользователь может изменять ширину столбцов таблицы требований, перетаскивая разделители. Настройки сохраняются в `localStorage` и привязываются к идентификатору пользователя, чтобы ширина столбцов сохранялась между сеансами.

### 11.3 Модальные окна

Для операций создания и редактирования используются модальные окна для:

- требования;
- группы;
- пользователей;
- настроек префиксов.

## 12. Хранилище данных

Система использует единый JSON-файл `data/database.json` как источник хранения.

Основные сущности данных:

- `users` — пользователи и их права;
- `requirements` — требования проекта;
- `groups` — иерархия групп;
- `requirementPrefixes` — префиксы для автоматической генерации номеров требований.

## 13. Бизнес-правила и ограничения

1. Администратор — единственная роль с полным доступом к административным функциям.
2. Все требования принадлежат конкретному проекту.
3. Требование может быть привязано только к существующей группе выбранного проекта.
4. Нельзя удалить группу, если она содержит требования или дочерние группы.
5. Нельзя перевести группу в родителя, который является ее потомком.
6. Номер требования уникален в рамках проекта и типа.
7. Пользователь видит только те проекты, которым назначен для чтения/редактирования.
8. Для создания или редактирования требования обязательны корректные значения статуса, типа и приоритета из справочников.

## 14. Критерии приемки

Приложение считается реализованным и пригодным к использованию в рамках MVP, если выполняются следующие условия:

- пользователь может войти в систему и открыть проектную область;
- можно создавать, редактировать и удалять требования;
- можно создавать, редактировать и удалять многоуровневые группы;
- фильтры и поиск корректно корректируют список требований;
- администратор может управлять пользователями и назначениями;
- префиксы требований формируются согласно правилам проекта и типа;
- система запрещает некорректные операции по бизнес-правилам.

## 15. Ограничения текущего MVP

1. Данные хранятся в JSON-файле, а не в реляционной базе данных.
2. Отсутствует масштабируемое многопользовательское конкурентное управление данными.
3. Поддерживается только локальное развертывание без внешней инфраструктуры.
4. Права и проектные назначения определяются в приложении вручную и не интегрированы с внешними системами идентификации.

## 16. Результат

Реализованная система обеспечивает базовый, но рабочий процесс управления требованиями: от авторизации и выбора проекта до создания иерархии групп, управления требованиями, фильтрации и администрирования пользователей и префиксов.
